# IME 输入法验证报告 — 2026-09-09（v1.2.26 后）

验证方式：源码审读 + dbus-monitor 真实格式模拟 + MC 26.1 jar API 核对 +
对照 Fcitx5-Enhancer / IMBlocker / native host_bridge（dbus_ibus.rs）。

## 结论：MC 主进程文本框 IME 链路是断的（Java ImeDispatcher 体系）

waylandcraft 有两套 IME 体系：

### A. native Rust 体系（nested wayland app 路径）— 基本完好
- `native/src/ime/mod.rs` + `host_bridge/dbus_ibus.rs`（976 行）+ dbus_fcitx5.rs
- 用 **portal 正确接口** `org.freedesktop.portal.IBus`（GNOME flatpak 同路）
- fire-and-forget ProcessKeyEvent + 信号回传 commit/preedit，状态机 + 测试齐全
- 服务对象：跑在 MC 里的桌面程序（firefox/xterm）——它们自己的文本框

### B. Java ImeDispatcher 体系（MC 主进程文本框路径）— 坏的
服务对象：MC 自己的聊天/命令/搜索框（用户真正打字的地方）。致命缺陷：

1. **[致命] Fcitx5DbusBackend dbus-monitor 解析器 bug**
   - 真实输出：signal header 单行含 `path=...; interface=...; member=...`，
     参数在后续行、空行分隔
   - 代码期望 `interface=` 出现在行首、`member=` 独立成行 —— 永不匹配
   - 模拟验证：**ZERO DISPATCHES** → commit/preedit 事件永远到不了游戏
   - 这就是"输入法不可用"的直接根因

2. **[致命] IbusDbusBackend 是纯 stub**（probe 恒 false / start 恒 empty）
   - 注释声称覆盖所有 ibus 引擎，实际一行实现都没有
   - Ubuntu/Debian 默认 ibus 用户完全无 IME

3. **[致命] 无接线**：registerTextField / onFocusedTextFieldChanged /
   notifyDeleteSurrounding / notifySurroundingText **零调用点**
   → 即使事件到达也找不到注入目标文本框，focus 状态机从不触发

4. **[方向反了] Fcitx5Session.commit(text)** 把字符串逐码点当 keysym
   回灌 fcitx5 ProcessKeyEvent——与 ImeBackend 接口语义（收 IME commit
   上屏）矛盾。KeyboardHandler 已把键给 MC，不应再喂 fcitx5。

5. dbus 目标也用错：`org.fcitx.Fcitx5`/老 `org.freedesktop.IBus`，
   而 native 侧验证过 portal 才对（Java 应为 `org.freedesktop.portal.IBus`
   或 fcitx5 的 `org.fcitx.Fcitx5` InputContext1——需实测确认）。

### C. 参考项目对照
- **Fcitx5-Enhancer**（NLR-DevTeam, MC 26.1+）：native `libfcitx5_detector.so`
  探测 + Mixin（EditBox/KeyboardHandler/Minecraft）拦截按键分流——不解析
  dbus-monitor 文本，直接 JNI。其 26.x 禁用了 native wayland 通道。
- **IMBlocker**（reserveword）：纯 Mixin 焦点状态机 + 多平台 IMManager，
  修"游戏热键 vs IME 激活"冲突——我们的 onModifiersChanged 想做的正是这个。
- **MC 26.1.2 原生**：KeyboardHandler.submitPreeditEvent(GuiEventListener,
  PreeditEvent) 是 static 真 API（javap 验证）；PreeditEvent record 构造
  (String,int,List<String>,int)。MC 已内置 IMEPreeditOverlay 渲染。
- **native dbus_ibus.rs** 是正确的 portal 接口范本（本仓库内就有正确答案）。

## 修复方案（Java 侧重写，对齐 native/参考实现）

M1 修 dbus-monitor 解析器：按真实格式解析 signal header 行
   （正则 `signal .* path=(\S+); interface=(\S+); member=(\S+)`）
M2 ibus/fcitx5 探测走 portal/正确 dest（对齐 native dbus_ibus.rs 常量）
M3 补接线：Screen/EditBox 打开时 registerTextField（仿 CursorRectReporter
   每 tick 找 focused 的现有逻辑 → 在 MinecraftMixin 里补 dispatcher 通知）
M4 方向修正：ImeDispatcher.injectCommit 是注入 MC（已有），删掉/反转
   Fcitx5Session.commit 的回灌语义；MC 原生 submitPreeditEvent 已渲染
   preedit——backend 只需收，不需发 keysym
M5 （可选）IMBlocker 式焦点状态机，对齐 Fcitx5-Enhancer 的按键分流

native A 体系不动（验证完好）。

## 追加验证（GLFW/MC 原生层，决定性）

- MC 26.1.2 的 KeyboardHandler 注册了 GLFW preedit/imeStatus callbacks：
  `InputConstants.setupKeyboardCallbacks(window, keyCB, charCB, preeditCB, imeStatusCB)`
  + `preeditCallback(long, PreeditEvent)` 处理 GLFW preedit 事件。
- LWJGL GLFW 3.4.1（MC 26.1.2 依赖）带完整 IME API：`GLFW_IME` input mode、
  `glfwSetPreeditCallback` / `glfwSetIMEStatusCallback` /
  `glfwSetPreeditCandidateCallback` / `glfwGetPreeditCursorRectangle`。
  （即 bczhc/glfw 合入 GLFW 主线的 IME 扩展）
- MC 只有渲染层（IMEPreeditOverlay）+ record（PreeditEvent/CharacterEvent），
  无自带 fcitx/ibus 对接 —— preedit 事件经 GLFW 从系统 IME 进来。

**结论修正**：MC 26.1.2 走"GLFW IME → KeyboardHandler.preeditCallback →
submitPreeditEvent → IMEPreeditOverlay"的**原生链路**（X11 走 XIM、Wayland 走
text-input-v3，由 GLFW 决定）。这正是"不依赖模拟层、原生兼容 Minecraft"的
官方路线。

**因此 Java ImeDispatcher → dbus 桥（Fcitx5DbusBackend/IbusDbusBackend）是
多余且有害的第三层**：它绕开 GLFW 原生链另建 fcitx5 IC，抢焦点、方向反、
解析器坏。waylandcraft 在 MC 文本框这条路上应**依赖 MC 原生 GLFW IME**，
只做两件事：
  1. 确保 GLFW_IME 开启 + 环境正确（XMODIFIERS 等）——用 mixin 探测/补设；
  2. 把桌面嵌套窗口的 IME 继续走 native Rust host_bridge（那条是给
     firefox 等桌面应用的，正确）。

修复范围修订：M1-M4（Java dbus 桥修复）改为 **Java dbus 桥降级为 fallback**：
  优先级 native GLFW IME > dbus 桥（仅当 GLFW IME 不可用时启用，如
  无 GLFW IME 的旧 LWJGL）。本轮已修的解析器 bug/focus 接线保留（作为
  fallback 路径的正确实现），不再作为主路径。
